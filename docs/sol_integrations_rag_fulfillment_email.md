Sol is the single autonomous agent that builds and runs each store (currently
`timeforbaby`, at `stores/shopify/hydrogen-timeforbaby/`, which also doubles as the
template for future stores). This document describes four capabilities that turn
Sol from "an LLM that sources products and writes code when asked" into "an agent
that runs the store's back office": a data-driven integration registry, two RAG
corpora, automatic order fulfillment, and a customer-email tool with an
inbox-polling heartbeat.

The unifying goal across all four: **make the template store-agnostic**. Every
piece of per-store detail (which supplier, which domain, which mailbox, which
credentials) lives as *data* on that store's row, not as code or config baked into
the template. Standing up store #2 on a different supplier and a different support
mailbox should require a new database row, not a code change.

## 1. Store Integration Registry

**File:** `src/stores/__init__.py` (`StoreConfig` dataclass + the SQLite `stores`
table it maps to).

### The problem

Before this change, anything integration-specific (which dropshipping supplier to
call, which mailbox to send customer email from) would have had to be hardcoded
per-store in Python or scattered across `.env`/config files. That doesn't scale
past one store, and it means the "template" store isn't actually a template — it's
a one-off with `timeforbaby`-specific assumptions wired into the code.

### What changed

`StoreConfig` gained five new fields (with matching SQLite columns and an
`ALTER TABLE ... ADD COLUMN` migration so existing rows upgrade in place):

| Field | Type | Purpose |
|---|---|---|
| `supplier` | `str` | Which dropshipping supplier this store sources from, e.g. `"cj"`. Defaults to `"cj"` today, but the field exists so a future store on a different supplier needs no code change — just a different value. |
| `supplier_credentials` | `dict` | Supplier-specific secrets (API keys, MCP tokens) — e.g. CJ's `api_key` / `mcp_key`. Read by `place_supplier_order()` instead of a single global CJ credential. |
| `support_email` | `str` | This store's customer-facing mailbox address, e.g. `support@timeforbaby...`. Used both to send outbound mail and to know which inbox to poll. |
| `email_credentials` | `dict` | Gmail OAuth refresh-token trio (`client_id`, `client_secret`, `refresh_token`) scoped to that mailbox — never a global company mailbox. |
| `integrations` | `dict` | Catch-all for anything added later. New integration types become new keys in this dict, not new columns/migrations. |

### Why this matters

Every downstream capability in this document (§2–§4) reads its per-store config
from this one row:

- The RAG "search local catalog" tool and `cj_add_product` read `supplier` /
  `supplier_credentials` to know which supplier API to hit and how to authenticate.
- `process_order()` (§3) reads `supplier_credentials` to place the CJ order for
  *that* store, and `support_email` / `email_credentials` to send the confirmation.
- The email tools (§4) read `support_email` / `email_credentials` to know which
  mailbox to send from and poll — never a hardcoded address.

This is the load-bearing design decision behind the whole doc: **the registry row
is the single source of per-store truth**, and everything else is generic code
that reads it.

## 2. Two RAG Corpora on Redis

**Files:** `src/rag/index.py` (new), `scripts/ingest_playbook.py` (new),
`docker-compose.yml` (Redis image swap).

### The infrastructure

- Redis moves from plain `redis:7-alpine` to `redis/redis-stack-server`, which
  bundles the Redis Search/vector module needed for similarity search.
- Vector operations go through **`redisvl`**, Redis's official vector library —
  no new vector database, no new embedding provider.
- Embeddings are generated by `src/embeddings/__init__.py`'s existing
  `embed_text()` (a local Ollama call to the `nomic-embed-text` model), reused
  as-is. No external embedding API, no added per-call cost — this was already
  running for store-description RAG and is simply pointed at two new corpora.

### Corpus A: CJ Product Catalog

**Populated by:** `search_trending_products` (`src/mcp_tools/sourcing.py`) and
`cj_add_product` (`src/org/agent_loop.py`) — every CJ candidate product either tool
has ever *seen* gets embedded (title + description) and stored with metadata:
`pid`, accept/reject verdict + reason, category, images, variants.

**The problem it solves:** without persistence, every sourcing pass re-queries CJ
from scratch and re-evaluates products Sol has already looked at — including ones
it already rejected (e.g. for having fewer than 3 images, per the hard 3-image
gate) — burning API calls and LLM reasoning re-deriving the same verdict.

**New tool:** `search_local_catalog(query)` searches this persisted corpus
*first*. Only if nothing local matches close enough does it fall back to a live
CJ API call. This means:
- Previously rejected candidates are remembered *and why* — they're never
  re-evaluated from a blank slate.
- Previously accepted candidates can be found again fast (e.g. "did we already
  source a nursing pillow like this?").
- Live CJ calls become the exception path, not the default one.

### Corpus B: Sol's Own Playbook

**Populated by:** `scripts/ingest_playbook.py`, a one-time/re-run-as-needed script
that chunks (by section) and embeds all of Sol's operating documentation:
`docs/*.md` and `guides/**/*.md` under `stores/shopify/hydrogen-timeforbaby/` —
things like `PRODUCT_UPLOAD_PIPELINE.md`, SEO guidance, QA guidance, and the
`productDisplay`/`search`/`predictiveSearch` guides.

**The problem it solves:** the old approach stuffed all of this operating
knowledge as growing static prose directly into Sol's system prompt on *every*
call, regardless of whether that particular task needed it. That's wasted tokens
on every single turn, and the prompt only grows as more playbook docs accumulate.

**New tool:** `search_playbook(query)` lets Sol retrieve exactly the relevant
guidance on demand — "why pick this kind of product", "what makes a good SEO
description", "how to showcase a product" — instead of always paying for the
entire playbook's token cost up front. The system prompt shrinks to Sol's core
identity/rules; domain knowledge becomes retrieval, not memorization.

### How both feed Sol

```
CJ API ──▶ search_trending_products / cj_add_product ──▶ embed ──▶ Corpus A (Redis)
docs/*.md, guides/**/*.md ──▶ ingest_playbook.py ──▶ embed ──▶ Corpus B (Redis)

Corpus A ──▶ search_local_catalog(query) ──┐
                                             ├──▶ Sol (run_sol_task, LLM tool loop)
Corpus B ──▶ search_playbook(query) ────────┘
```

Both are just new tools bound into Sol's existing tool loop (`run_sol_task` in
`src/org/agent_loop.py`) alongside its existing CJ/Shopify/code tools — Sol
decides when to call them, the same way it decides to call any other tool.

## 3. Automatic Order Fulfillment

**Files:** `src/api/routes/webhooks.py` (existing `orders/create` receiver),
`src/org/fulfillment.py`'s `process_order()` (new), `src/mcp_tools/fulfillment.py`
(existing `place_supplier_order()` / `fulfill_shopify_order()`, now wired up),
`src/org/tickets.py` (existing ticket board), `src/org/agent_loop.py`'s
`run_sol_task` (existing LLM loop, now invoked on failure).

### The problem

Shopify already sends an `orders/create` webhook (HMAC-validated in
`src/api/routes/webhooks.py`), but until now the handler just acknowledged it and
did nothing — every order had to be fulfilled by hand.

### The happy path (deterministic, no LLM)

For each order line item:

1. Read its **SKU**. No separate product-mapping table is needed because Sol's
   product-creation tool already stores the CJ variant id directly as the Shopify
   variant's SKU — the SKU *is* the CJ lookup key.
2. Call the already-existing **`place_supplier_order()`**
   (`src/mcp_tools/fulfillment.py`), using *that store's* `supplier_credentials`
   from the registry (§1) — places the real CJ dropshipping order.
3. On success, call the already-existing **`fulfill_shopify_order()`** — pushes
   tracking back to Shopify (which triggers Shopify's own shipping-notification
   email), and additionally sends a branded confirmation via Sol's email tool
   (§4) from that store's `support_email`.

This path is deliberately **scripted and cheap** — no LLM call happens here. It's
plain function calls chained together, because the happy path is fully
predictable and shouldn't burn LLM tokens or add LLM latency/non-determinism to a
transactional flow.

### The unhappy path (LLM-in-the-loop)

On any failure — a CJ API error, a bad/incomplete shipping address, an unknown or
unmapped SKU — `process_order()` does **not** retry on a fixed schedule. Instead
it:

1. Opens a ticket on the existing ticket board (`src/org/tickets.py`), with the
   specific failure reason attached.
2. Hands that ticket to Sol's own reasoning loop (`run_sol_task`) to investigate.

Sol then uses judgment that a scripted retry can't: deciding whether to retry the
CJ call, looking up what actually went wrong with the address, checking
`search_local_catalog`/order history to resolve an unknown SKU, and — if there's
a genuine delay — emailing the customer proactively via the email tool (§4) to
explain, rather than leaving them silently waiting.

```
Shopify "orders/create" webhook
        │
        ▼
process_order()  (deterministic, no LLM)
        │
        ▼
place_supplier_order()  ── uses store's supplier_credentials (§1)
        │
   ┌────┴────┐
 success    failure
   │          │
   ▼          ▼
fulfill_shopify_order()      open ticket (tickets.py)
   +                                │
send confirmation email             ▼
(support_email, §4)          run_sol_task investigates,
                              retries / emails customer about delay
```

This is the general pattern for how Sol handles operational work going forward:
**deterministic code for the predictable 95% of cases, LLM reasoning reserved for
genuine exceptions** — keeping the system both cheap and reliable.

## 4. Customer Email Tool

**Files:** `src/mcp_tools/email.py` (new), `src/org/heartbeat.py` (existing
periodic proactive-turn tick, extended).

### The tool

`src/mcp_tools/email.py` is a Gmail API wrapper using the OAuth2 refresh-token
flow, exposing three primitives:

- `send_email`
- `check_inbox`
- `mark_handled`

All three read `email_credentials` / `support_email` from the store registry
(§1) — **never** a global mailbox. This is what makes it safe for multiple stores
to each have Sol answer customer email independently, correctly attributed and
correctly authenticated per store.

Two of these are exposed as Sol tools: `send_customer_email` and `check_inbox`.

### The heartbeat integration

Sol's heartbeat (`src/org/heartbeat.py`, its existing periodic "proactive turn"
tick) gets a cheap inbox-poll added. Each tick:

1. Calls `check_inbox` for the store's mailbox — a cheap, non-LLM API call.
2. For each new **unread** customer email found, kicks off a full
   `run_sol_task` so Sol:
   - reads the message,
   - pulls whatever context it needs (`search_local_catalog` for product
     questions, `search_playbook` for policy/process questions, order lookups
     for "where's my order" questions),
   - replies via `send_customer_email`,
   - marks the thread handled via `mark_handled` so it isn't re-processed next
     tick.

```
heartbeat tick ──▶ check_inbox(support_email)
                        │
                 unread email found?
                        │ yes
                        ▼
                 run_sol_task(...)  ⇄  search_local_catalog / search_playbook / order lookups
                        │
                        ▼
                 send_customer_email(...)  ──▶  mark_handled(...)
```

### Fully autonomous by design — with a staging step

Sending is fully autonomous on purpose: this is the store owner's explicit
choice, not an oversight. But the rollout path includes a deliberate staging
step before it touches real customers:

1. Point a store's `support_email` at a **throwaway test Gmail inbox**.
2. Send Sol some realistic test customer questions directly via
   `run_sol_task(...)` (bypassing the heartbeat trigger, so it's on-demand).
3. Read Sol's real replies in that test inbox and confirm they're correct, on
   brand, and appropriately scoped.
4. Only then switch `support_email` to the real support address and turn on the
   heartbeat's automatic inbox polling.

This lets the owner validate Sol's actual customer-facing writing and judgment
before any real customer ever sees an autonomous reply.

## Cross-Cutting Summary

All four pieces share the same shape: **read per-store config from the registry
(§1), do the deterministic/cheap thing first, and only escalate to Sol's LLM
reasoning loop (`run_sol_task`) when genuine judgment is required** — vetting a
CJ candidate against remembered rejections, answering a question that needs
playbook nuance, handling an order that failed in an unscripted way, or replying
to a customer email that a template response can't cover. The result is a system
that scales to new stores by adding rows, not by adding code, and that keeps LLM
usage concentrated where it actually earns its cost.
